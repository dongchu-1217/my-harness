# 검증과 리뷰 (R8)

## 확인된 사실

| 항목 | 결과 |
|---|---|
| Python | 3.9.6 (`judge.py`는 3.9 문법으로 작성한다.) |
| Node | 있음 (G5의 HTML 스크립트 구문 검사에 사용: `node --check`) |

| `QGROUPS` | `[질문, 0, 1, 답변 문장들, 키워드]` 형태의 위치 기반 배열. 가운데 숫자 두 개의 의미는 미확인 |

| 기존 HTML 내용 | 원본에는 실제 경험과 수치가 들어 있었다(현재 저장소 버전은 샘플 더미 데이터로 변환됨). `harness/data/experiences.json`은 최초 0건이다. |

## 검증

| 검증 | 내용 | 통과 조건 |
|---|---|---|
| V1 게이트 테스트 | 게이트 6개(G1~G5, 사람 승인)마다 통과 1건·실패 1건 | 12/12 케이스 통과. ★ 위반 조건(G2, G4, 승인 전 S5)의 실패 케이스가 모두 걸린다. |
| V2 드라이런 | 샘플 JD 1건으로 S1~S4 실행 | `state.json`이 S4 통과로 기록, 실행 폴더 파일 5개 |
| V3 독립 리뷰 | `judge.py`와 `CLAUDE.md`를 읽기 전용으로 리뷰 | 확인된 지적 0건이 될 때까지 수정 |

- 테스트용 샘플 JD·경험 카드는 `harness/tests/`에만 둔다. 실제 `harness/data/experiences.json`에는 넣지 않는다.

## G5 보존 기준 변경
- 변경 전: 반영 전 항목 ID 보존(사라진 항목 0건)
- 변경 후: 상수를 평가한 값으로 비교해 반영 전 내용이 값까지 그대로 남아 있어야 한다(추가만 허용). (id·문자열 개수 비교는 레벨·덮어쓰기를 못 잡아 대체)

## 결과

### V1 게이트 테스트 (harness/tests/run_tests.py)
- 핵심 12/12 통과 (게이트 6개 × 통과 1 + 실패 1)
- ★ 위반 조건 케이스 7/7 걸림
- 전체 57/57 통과 (독립 리뷰가 지적한 우회 경로 케이스 포함)

### V3 독립 리뷰 (읽기 전용 서브에이전트)
- 지적 10건. 재현 스크립트를 직접 돌려 확인한 뒤 반영했다.
- 승인 게이트가 `04-check.json`(자기보고 파일)만 믿음 → 승인 시 G1~G4 재판정 + 카드·review.md 해시 고정
- G5가 승인 여부를 안 봄, 허위 항목 추가·덮어쓰기를 못 잡음 → G5가 승인을 재확인하고, 평가된 값으로 '기존 내용 그대로 + 새 문자열은 승인된 카드에 있음'을 판정
- G4 숫자 추출 구멍(영문 뒤 숫자, 쉼표, 미등록 단위, 소수) → 추출 규칙 보강, 인용한 경험 원문만 대조, 'A/B' 용어 대조 추가
- 스키마 밖 키, 빈 문자열 목록, 문자열 횟수, 비정상 입력 크래시 → 허용 키 검사, 빈 값 판정 강화, 입력 오류도 JSON으로 응답(종료 코드 2)
- 문서·코드 불일치(CLAUDE.md, pipeline.md, artifacts.md) → 정리

### 남은 한계 (gates.md에 명시)
- 숫자 없는 허위 서술과 한글 수사(절반, 두 배)는 스크립트가 못 잡는다. 사람 승인에서 원문 대조로 확인한다.
- 질문 문구의 서수·시간 제한('3가지', '1분')도 G4에 걸린다.

### V2 드라이런 (harness/tests/dryrun/, 테스트 데이터·테스트 사본)
- 샘플 JD(요구사항 7개)와 경험 카드 2개로 S1~S5를 실제 에이전트(card-writer, index-writer)로 실행. 판정은 오케스트레이터가 judge.py로 직접 실행(에이전트 정의가 이 세션에 로드되지 않아 judge 에이전트는 쓰지 않음)
- 게이트: G1~G4 통과, 승인 게이트 통과, G5 통과. S3 되돌아가기 1회
- 실행 폴더 파일: 8개 (01~04, review.md, state.json, 05-index-before.html, 05-changelog.md) = artifacts.md의 S5 통과 조건 8개와 일치
- 실제 인덱스 HTML은 변경되지 않음 (해시 일치). 테스트 사본에는 추가만 반영(21줄)
- 지어낸 경험·수치 0건. 경험 카드에 없는 3건은 `경험 부족/확인 필요`로 분류
- 발견: card-writer가 03 꼬리 질문 본문에 `확인 필요` 주석을 넣음 → pre-review가 걸러 냄 → card-writer 지침에 '확인 필요는 02에만' 규칙 추가, S3 재실행
- 한계: pre-review(`확인 필요` 잔존)는 02의 정상 표시도 걸러 사용자 확인으로 넘긴다. 승인 단계가 사람의 원문 대조를 요구한다.

## 범위 결정
- 기존 HTML 내용을 `harness/data/experiences.json`으로 가져오지 않는다. 기존 내용은 G5로 보존만 지킨다.
- G4 수치 검증은 새로 입력한 경험 카드만 대상으로 한다.
- 편집 범위 강제 훅은 만들지 않는다.
