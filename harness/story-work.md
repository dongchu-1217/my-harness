# 작업 방식 (AI 없이 손으로 했던 마지막 경험)

`story-service.md`는 면접 준비자가 "무엇을 위해" 쓰는지의 기준이고, 이 문서는 **이 서비스의 화면을 만드는 디자이너**가 "실제로 어떻게 작업했는지"다. 둘은 섞지 않는다.

## 작업 문장 7개

1. 나는 uibowl에서 경쟁사 레퍼런스를 수집한다.
2. 레퍼런스를 토대로 분석하고 우리 서비스에 반영할 부분을 가져온다.
3. 분석 내용을 토대로 우리 서비스 화면 설계 문서를 구체화한다.
4. Figma에 레퍼런스와 화면설계서를 반영한 UI 키스크린 2~3개를 390×844 사이즈로 그린다.
5. 내부 관계자들과 협의 후 컨셉 시안을 확정한다.
6. 컨펌된 시안을 기반으로 디자인 토큰과 컴포넌트를 제작하고, 화면 디자인에 들어간다.
7. 완성된 시안에서 토큰이나 컴포넌트가 우리 가이드에 위반된 부분이 없는지 검토한다.

## 명사 · 게이트 · 경계

| # | 명사 (산출물) | 게이트 (사람이 판단하는 지점) | 넘어가는 곳 (경계) |
|---|---|---|---|
| 1 | 경쟁사 레퍼런스 | 레퍼런스가 충분한지 보고 분석 단계로 넘어갈지 판단 | uibowl (도구) |
| 2 | 분석 내용, 우리 서비스에 반영할 부분 | 무엇을 우리 서비스에 반영할지 판단 | 없음 |
| 3 | 화면 설계 문서 | 설계가 충분한지 보고 시안 단계로 넘어갈지 판단 | 없음 |
| 4 | 키스크린 시안 2~3개 (390×844) | 없음 | Figma (도구) |
| 5 | 확정된 컨셉 시안 | 내부 관계자 협의 후 확정 | 내부 관계자 (사람) |
| 6 | 디자인 시스템 산출물 (토큰·컴포넌트·화면 디자인 묶음) | 없음 | 없음 |
| 7 | 가이드 위반 검토 결과 | 토큰·컴포넌트가 가이드를 위반했는지 판단 | 없음 |

## 메모

- 게이트 1·3의 "충분한지 판단"은 구체적인 판단 기준이 아직 정해지지 않았다.
- 경계는 문장에 적힌 uibowl, Figma, 내부 관계자만 확인되었다.
